1. State Layer

Architecture

The state layer owns row data, sort order and selection. It has no opinion about markup — every behavior is exposed as a signal your template reads, so the same state can drive a table, a list, or a virtualized window.

Signals as the contract

Every piece of table state is a signal. Reading rows() in a template subscribes that view to changes; nothing else is required. There is no change detection to configure and no lifecycle to observe.

ⓘ
Zoneless by default
The state layer never calls into NgZone. If your app still runs zone-based change detection, nothing breaks — the signals simply notify twice as cheaply as they need to.

Deriving sort order

Sorting is a computed signal over the source rows. It never mutates the input array, so the data you passed in stays exactly as you passed it.

const sorted = computed(() => {
  const key = sortKey();
  if (!key) return rows();
  const dir = sortDir() === 'asc' ? 1 : -1;
  return [...rows()].sort((a, b) => compare(a[key], b[key]) * dir);
});

Stability

The comparator is stable: rows that compare equal keep their original relative order. This matters for multi-column sorting, where a second sort must preserve the first.

⚠
Comparators run on every read
Keep them pure and cheap. A comparator that formats dates or hits a locale API will dominate render time at a few thousand rows.

Selection

Selection is stored as a set of row keys rather than row objects, so it survives a refetch. If the same key comes back with new data, the row stays selected.
