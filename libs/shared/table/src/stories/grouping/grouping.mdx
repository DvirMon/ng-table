# Grouping

Five stories, in the order worth reading them. **`Static` is the one to copy** — its host composes
`withGrouping()` alone, so nothing in its source is another feature's setup. `Regressions` is
deliberate misuse and is marked so. The other three each compose grouping with one more feature.

Shared across all five: `fixtures/schema.ts` (one column list, one config, and the grouping levels
that do differ per story), `fixtures/http.ts` (the intercepted round trips),
`grouping-story.pipes.ts` (one pure pipe per formatting concern, so no host formats in a method)
and `grouping-story.css`. Those are at the bottom of this page, once.

---

## Static — the grouped table as its own product

`withGrouping()` and nothing else. Every other story on this page composes grouping with one more
feature; this one composes none, so its source is copyable as-is — including deliberately **no**
`withExpansion()`, because a chevron with nothing to expand is a control that does nothing. Group
headers carry value, count and `amount` total at every depth.

Aggregates are post-filter by construction (`filter` precedes `group` in the pipeline), but the
control that proves it lives in `Group selection` below, which composes `withFiltering()` for its
own reasons — not here.

The tab strip toggles a column as a level; the pills below reorder and remove them. One control per
column, one boolean state, so adding a duplicate level is unreachable from the UI rather than a
no-op to explain.

## Async Rule — a level decided by the server

One grouping level over a real intercepted request, through an `applyGroupingAsync()`-shaped column
rule. The point is the *pending* window, which is otherwise invisible: while the rule is unresolved
the whole rule set abstains and the table holds the grouping it was given, rather than flashing
ungrouped and back. On resolution the level set becomes the rule's — a resolved rule overrides the
base choice rather than merging with it.

`onError` is required to return an explicit boolean: `false` here, resolving the set to `[]`, which
is "grouped by nothing" rather than "no answer yet", and leaves every row on screen. Turn on
`forceFailure` in Controls to see it — one boolean away from the resolved case, so it is a control
rather than a second canvas.

## Regressions — **do not copy this host**

The grouping gaps that are still open, kept on screen instead of in a bug list. Every control here
drives deliberate misuse.

Two of them degrade **silently**. *Group by a column that is not there* adds a level naming no
column: the table groups by the rest and says nothing, so the notice on canvas is the story's own
arithmetic rather than a library report. *Break one group's summary* poisons one row's `amount`,
and the whole table goes down instead of that one summary blanking
([#79](https://github.com/DvirMon/acme/issues/79)).

<Canvas of={RegressionsStories.SilentDegradation} />

The third is pinned as its own story because `throwing` is one of five options in a select — a
state nobody finds by accident, unlike the buttons above. The comparator throws on every sibling
pair it is handed and the table does not go down: the clustering sort catches, falls back to stable
first-occurrence order for the affected levels, and reports once per evaluation.

## Collapsible — the navigable outline

`withGrouping()` + `withExpansion()` + `withSorting()`: a real `<button>` chevron carrying
`aria-expanded`, the whole header row as hit area, and subtree collapse. A deal carrying `children`
renders a second, separately-keyed chevron from the `'tree'` stage.

<Canvas of={CollapsibleStories.Collapsible} />

Three attacks on the collapse state live here — Refetch with freshly-constructed rows, sort
toggles, and a Regroup that changes every group id at once. Forced failure is the fourth: refetch
fails every time instead of returning a fresh page, so nothing is replaced, an error line appears,
and the collapse state is untouched. A failed refresh must leave an outline exactly as it was,
which is the half of product story 2.5 that `Default`'s DOM never reaches.

## Group selection — three cascades, one `rowsOf()`

The `cascade` control is this story's whole argument, not a convenience. D16 made the
group-selection cascade consumer-owned precisely because the three major libraries ship three
different defaults, so a single hardcoded cascade in a story would read as the library taking a
position it deliberately does not take. All three are written here as ordinary code over one
`rowsOf()` call, with tri-state group checkboxes derived rather than stored, and a readout proving
no group header is ever in the selection.
