# Filtering

Three stories over one question: where the filtering happens. `Client` feeds a filter model into
the pipeline, `Server` serializes the same model into a request, and `Predicates` composes no
model at all. `Selection × Filtering` moved to [`Table / Selection`](?path=/docs/table-selection--docs)
— its focus is selection surviving another feature's row churn, not filtering itself.

Shared: `fixtures/schema.ts`, `fixtures/http.ts` and `filtering-story.css`, at the bottom of this
page. `Predicates` brings its own schema, shown in its own tab.

---

## Client

`withFiltering({ predicates: () => [filters().matcher()] })` feeds a standalone `createFilters()`
object into the pipeline's `filter` stage as one predicate term. The feature takes row predicates,
not a filter model; the host composes the two. The filters are the consumer's — the feature owns no
filter state — which is why the same declarations feed a server request unchanged in `Server`.

One filter may target one path, so the `tags` column's include and exclude halves are a single
compound `filter()` criterion fed by two multi-selects, and the quick filter spans `note` and `id`
rather than borrowing `customer`, which already carries its own `contains`.

## Server

No filtering feature is composed here. `withFiltering({ predicates: () => [], manual: true })`
exists for symmetry with `withSorting()`, but in server mode it is an identity pass-through that
still claims the `filter` stage — composing it would occupy a slot to do nothing. The same
`createFilters()` object the client story turns into a predicate via `matcher()` is serialized into
`GET /api/invoices` instead, and the rows arrive already narrowed.

The query mapping is hand-written in the host on purpose: no library can know a given backend's
parameter names, so that code is what a consumer actually writes.

<Canvas of={ServerStories.Server} />

Under failure, every request fails. Unlike the happy path, the canvas keeps whatever rows loaded
last — they stay on screen behind an error marker instead of the table blanking — and a Retry
button re-sends the current filter set rather than resetting it. The filter inputs are untouched by
the failure, so the retried query is the one that failed, not a fresh one.

## Predicates

This table filters with plain handwritten predicates and composes **no filter model at all** —
`withFiltering({ predicates })` takes a thunk returning `(row) => boolean` terms, and the host
imports nothing from the filters domain: no `createFilters()`, no `Filters` type, no rules, no
matchers. That absence is the point; the sibling stories cover what a filter model adds.

The thunk is called once per filter pass, so terms built from ordinary signals re-narrow when those
signals change. Terms are AND'd, and a control with nothing in it contributes no term.
