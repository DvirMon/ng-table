# Server Filtering

No filtering feature is composed here. `withFiltering({ manual: true })` exists for symmetry with
`withSorting()`, but in server mode it is an identity pass-through that still claims the `filter`
stage — composing it would occupy a slot to do nothing. The same `createFilters()` object the
client story hands to `withFiltering()` is serialized into `GET /api/invoices` instead, and the
rows arrive already narrowed.

The query mapping is hand-written in the host on purpose: no library can know a given backend's
parameter names, so that code is what a consumer actually writes.

## Forced failure

Every request fails. Unlike `Default`, the canvas keeps whatever rows loaded last — they stay on
screen behind an error marker instead of the table blanking — and a Retry button re-sends the
current filter set rather than resetting it. The filter inputs are untouched by the failure, so
the retried query is the one that failed, not a fresh one.
