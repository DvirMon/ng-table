# Step 2 — The generator carries `TId` into every slot

**PR scope:** standalone. **Depends on:** Step 1 (`TableStore<TRow, TId>`
must exist before the generator can emit it).

**Task type:** chore

**Skills used:** —

**Scaffolding agent:** main thread, no agent

## Files

- `libs/table/tools/generate-overloads.ts` (edit)
- `libs/table/src/api/create-table.overloads.ts` (**regenerated**, never
  hand-edited)
- `libs/table/src/api/features/compose-features.overloads.ts` (unchanged —
  see below)

## Why This Step Exists

Step 1 gave the store a slot for the union. This is the step that puts a
feature's `In` on the type that has it. Until the accumulation base is
`TableStore<TRow, TId>`, slot 1 is typed `Feature<TableStore<TRow>, O1>`
and `ColumnIdOf<In>` resolves to its `string` fallback at every call site —
the plumbing exists and carries nothing.

The generated files are the only place this can change. Hand-editing
either one is what AC #5 forbids, and
`npm run table:overloads:check` is the gate that catches it.

## What To Do

**1. `tools/generate-overloads.ts` — the `CREATE_TABLE` spec's base.**

```ts
base: 'TableStore<TRow, TId>',
```

`baseGenerics` and `leadingParams` are already correct
(`['TRow', 'TId extends string']`, `config: TableConfig<TRow, TId>`) — the
generic was always bound, only the base dropped it.

**2. Delete the stale comment above `baseGenerics`.** It currently reads
that `TId` "is inferred from `config` … but never reaches the accumulation
base — no feature or the returned `TableStore` names a column id any more
(D7: grouping moved to row-keyed paths)." Every clause of that is now
false: D7 is reversed by ADR-0024, and this step is what makes it reach the
base. Replace it with one line stating that `TId` flows from
`config.columns` into every slot's `In` and into the return type, citing
ADR-0019 and ADR-0024 — no history, per
`.claude/rules/terse-jsdoc-for-ai-and-humans.md` § "No decision narration
in source comments".

**3. Regenerate.**

```bash
npm run table:overloads
```

Diff the result before accepting it. The expected change is mechanical and
uniform: 16 signatures, each `TableStore<TRow>` → `TableStore<TRow, TId>`
in every `Feature<…>` argument and in the return intersection. Output is
Prettier-formatted by the generator itself, so there should be no
whitespace-only churn.

**4. `compose-features.overloads.ts` is not regenerated, and does not
change.** Its base is `In extends Shape`, which is bound at the call site
to the concrete `TableStore<TRow, TId> & O1 & …` the enclosing
`createTable()` slot supplies. `ColumnIdOf<In>` therefore recovers the
literal union through the composite with no generator change at all — the
arity escape hatch carries the union structurally. Step 3 proves this and
Step 4 records it as the answer to AC #4. **If Step 3's `composeFeatures`
case fails, this step is what reopens** — the fallback is a `TRow`/`TId`
pair on `COMPOSE_FEATURES`'s `baseGenerics`, which is a materially bigger
change and needs its own decision.

## Implementation Notes

- **Run the generator, do not replicate it.** `npm run table:overloads`
  writes both files; `-- --dry-run` prints instead. The emitted header
  (`Generated by … — do not edit`) is the contract.
- **`ARITY` stays 15.** D27's cap is not in scope.
- **This is a `chore` step on purpose.** The hand-written change is two
  lines in a tooling file; the 547-line diff is machine output. Routing it
  to an implementer agent would put a generated file under an agent's
  authorship.

## Risks / Watchouts

- **A `TId` in the base can change inference on an existing call.** With
  `TableStore<TRow, TId>` in slot 1's `In`, TypeScript now has a second
  inference site for `TId` (the feature argument) alongside `config`. The
  story hosts and `create-table.spec.ts` are the real-consumer surface that
  would show it — both typecheck targets must pass before this step is
  done, not just the lib one.
- **`makeColumns()` in `api/create-table.spec.ts:20-36`** deliberately
  omits a `ColumnDef<Row>[]` return annotation so the ids stay literal. If
  that file starts failing after regeneration, the cause is inference
  order, not the fixture — do not "fix" it by annotating, which is exactly
  the silent widening #113 exists to guard against.
- **`npm run llms:check`** reads the public surface. It is Step 4's check,
  but if the regenerated signatures shift it, that surfaces here first.

## Non-Goals

- **No change to `compose-features.overloads.ts`**, per the reasoning
  above. Reopening it is a decision, not a fix.
- **No arity change**, no new overload shapes, no change to the
  accumulation rule (D27).
- **No spec.** Step 3 owns the proof.
