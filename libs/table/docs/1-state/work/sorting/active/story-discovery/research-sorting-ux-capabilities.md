# What can a person click and press to sort a table, in TanStack Table, AG Grid, MUI X Data Grid and PrimeNG?

**Date:** 2026-09-17 · **Mode:** competitor-capabilities

## Answer

- **Three-state click cycle is not universal.** AG Grid and MUI X both cycle `asc → desc → none` by default and let a person click their way back to unsorted. TanStack does the same but the developer must wire the click. **PrimeNG has no unsorted state at all** — its own docs tell integrators to write a custom sort function to get one back.
- **The multi-sort modifier splits 2–2.** AG Grid and TanStack default to **Shift**; MUI X accepts **Ctrl or Shift**; PrimeNG hard-codes **Ctrl/Cmd** with no option to change it. Three of four ship a numbered priority badge; TanStack ships the index and no badge (headless).
- **Null ordering is not universally silent — but only one library documents a policy.** TanStack documents `sortUndefined` with five named values including direction-independent `'first'`/`'last'`. The other three all implement a null rule in code and none states it in prose. AG Grid and MUI put nulls first ascending / last descending; PrimeNG pins empties at the **bottom in both directions** ("Excel like"), the opposite convention, undocumented.
- **The paywall lands in one place: multi-sort.** MUI X meters plain multi-column sorting behind **Pro**. AG Grid ships multi-sort, sort badge, keyboard sort and grid-state persistence in **Community**, and meters only sorting _of things that are themselves Enterprise_ (row groups, server-side row model). That contrast is the sharpest finding here.
- **Keyboard sorting is a real differentiator.** AG Grid and MUI X both define `Enter` to sort and `Shift+Enter` to multi-sort from a focused header. PrimeNG supports Enter/Space for single sort but has no keyboard path to multi-sort. TanStack has none, by design.

### Reliability notes that change how a claim should be read

- **A rendered-docs summary disagreed with the repo markdown on TanStack's own cycle order.** A web-search snippet of the sorting guide states the cycle is `'none' -> 'desc' -> 'asc'`; the repository markdown read directly says `'none' -> 'asc' -> 'desc' -> 'none'` for a string column. This document uses the repository markdown. Treat any second-hand quote of TanStack's cycle as suspect — the direction is data-type dependent and easy to paraphrase wrongly.
- **PrimeNG's docs page and PrimeNG's shipped code disagree about removable sort.** An automated fetch of `primeng.dev/table` summarised the behaviour as "clicking a column header cycles through ascending, descending, and unsorted". The shipped bundle contains **zero occurrences of `removable`**, and PrimeNG's own showcase doc says removable sort "can be implemented using the `customSort` property". Code and showcase source win over the rendered summary.
- **`removableSort` exists in sibling PrimeFaces products, not in PrimeNG.** Searching for the name will surface PrimeVue/PrimeReact material. Do not transfer it.
- **"Enterprise" in an AG Grid page header is not the same as "sorting is Enterprise."** The grouping-sorting and server-side-sorting pages are Enterprise because _row grouping_ and the _server-side row model_ are Enterprise, not because sorting is. The Community package's own `GridState` interface carries `sort?: SortState`, which is what settles the persistence question.
- **A null-handling rule found only in source is a behaviour, not a contract.** For AG Grid, MUI X and PrimeNG the rule below is read from shipped code; none of the three states it in prose, so it is not a promise any of them has made to a person and could change in a minor release.

Two further PrimeNG oddities, both read from shipped code and both unmentioned in the docs:

- `Table.compareValuesOnSort()` calls `ObjectUtils.sort(value1, value2, order, this.filterLocale(), this.sortOrder)` — it passes **`this.sortOrder` into the `nullSortOrder` parameter** [P2][P3]. When `sortOrder` is `-1` (descending), `finalSortOrder` becomes `-1` rather than the default `1`, so the empties-at-bottom rule is reached by a different path than the comment describes. Flagged as an observation about the implementation, not a claim about a bug.
- PrimeNG's **own showcase comparator contradicts PrimeNG's built-in**: the removable-sort demo returns `-1` when `value1 == null`, putting nulls **first** in ascending — the opposite of the framework's Excel-like bottom pin [P4][P3].

## Synthesis — where they disagree

**Cycle — PrimeNG is alone, and it is alone on the side that costs a person something.** Three of four treat "back to the order the data arrived in" as a state a person can click to. PrimeNG treats sorted-ness as permanent for the session, and its own documentation's answer is a ~25-line component the integrator writes, holding a tri-state flag and calling `dt.reset()` [P4]. The product decision this exposes: is "unsorted" a _state_ or an _absence_? Everyone except PrimeNG models it as a state, and PrimeNG's docs having to teach a workaround is evidence that modelling it as an absence was the wrong call.

**Modifier key — the disagreement is about macOS and about discoverability.** AG Grid picks Shift, PrimeNG picks Ctrl/Cmd, MUI accepts both, TanStack makes it a predicate. MUI accepting both is the only choice that cannot be wrong for a person arriving from another grid, and it costs nothing: the modifier is not used for anything else in the header. Separately, **three of four now ship a no-modifier mode** (`alwaysMultiSort`, `multipleColumnsSortingMode="always"`, `isMultiSortEvent: () => true`). That convergence says the industry has conceded the modifier is undiscoverable, and that some products would rather make multi-sort the default interaction than teach a chord. PrimeNG has no such mode.

**The badge is where headless stops being free.** TanStack hands over `column.getSortIndex()` and stops. The other three render the number. The interesting one is PrimeNG, which gates the badge on `multiSortMeta.length > 1` [P2] — so the badge appears only once a _second_ column is sorted. That is a defensible micro-decision (a "1" next to a lone sorted column is noise) and none of the other three appear to make it. If a badge is built, this is the detail worth copying.

**Nulls — the sharpest disagreement, and the one nobody has written down.** Two camps:

- _Direction-relative_ (AG Grid, MUI X, and TanStack's numeric `sortUndefined`): nulls are just "smaller than everything", so they flip ends when the person clicks again.
- _Pinned_ (PrimeNG's Excel-like bottom, TanStack's `'first'`/`'last'`): nulls stay put regardless of direction.

Both are defensible and they produce visibly different screens, which is exactly why leaving it undocumented is the wrong call — and three of four leave it undocumented. The evidence that direction-relative is unsatisfying in practice: **MUI's own docs devote a demo to escaping it**, teaching `getSortComparator()` specifically "to keep the `null` values at the bottom … regardless of the sorting direction" [M1]. A library whose documentation teaches how to get out of its own default has told you what the default should have been. The strongest available position is TanStack's: make it a named, per-column option, with both camps reachable, and _write it down_. The gap even TanStack leaves is that its option covers `undefined` and not `null` [T2] — for data that came from JSON or from SQL, `null` is the value that actually shows up, and it silently falls through to the comparator.

**Grouping — two opposite philosophies about who owns sort priority.** PrimeNG injects the group field at priority 0 on every multi-sort and then hides it from the badge numbering [P2]: the group ordering is not negotiable and is not shown as a sort. AG Grid instead treats group ordering as the group column's own sort, makes it visible, and adds `groupMaintainOrder` so a person's leaf-column sort can be prevented from reshuffling groups [A4]. AG Grid's is the honest model — the person can see why the groups are in that order — but PrimeNG's costs nothing to build. The decision to take is whether the injected group sort is _visible_ in the header UI; hiding it is what makes "why did my sort become number 2?" unanswerable.

**Keyboard — AG Grid and MUI agree on `Enter` / `Shift+Enter` and that agreement is worth treating as the convention.** Two independent vendors landing on the identical binding, unprompted by any APG recommendation, is the closest thing to a standard available. PrimeNG supports Enter and Space for single sort but has no keyboard route to multi-sort at all [P2] — a person who can only use a keyboard cannot reach a feature PrimeNG otherwise ships free. That is an accessibility gap, not a preference.

**The paywall contrast answers "is multi-sort expensive or is it metered?"** AG Grid gives away multi-sort, the priority badge and keyboard multi-sort in Community, and PrimeNG and TanStack give them away too. MUI X is the only one charging, and it charges for the _plain_ version — not for anything computationally harder. Three vendors giving it away establishes that multi-sort is not expensive to build; MUI charging for it establishes that people will pay for it anyway. The line MUI draws is "one criterion is a table, several criteria is a tool."

## Not researched

- MUI X **Premium** row grouping / aggregation and how sorting interacts with either. The Premium docs were not opened.
- MUI X **tree data** and AG Grid **tree data** sorting.
- AG Grid **pivot** sorting (`pivotSortModel` appears in `GridState` [A7] but the pivot docs were not read).
- Any **mobile / touch** sorting affordance in any of the four (long-press, header menu on small screens).
- Sorting via a **column header menu item** rather than a click, in AG Grid and MUI X. Both have header menus; whether they expose "Sort ascending" entries was not checked.
- **Community-pain sources** — issue trackers, feedback portals and forums were not read. This is a capability survey only; the `community-pain` node owns that.
- **Performance** of any comparator on large row counts, beyond AG Grid's own note that `accentedSort` "is slower than default sort" [A1].
- Angular-specific wrappers: `ag-grid-angular` and `@tanstack/angular-table` were read only through their shared core docs.

## Unverified

- **PrimeNG's `loading` input in relation to sorting.** The input exists on `p-table`, but nothing read ties it to the lazy sort round-trip. Confirm by reading the `p-table` lazy-loading showcase doc in `primefaces/primeng`.
- **Debounce on server-side sorting.** No documented debounce in any of the four. Absence of a mention is not proof of absence — confirm by reading each server-mode demo's handler.
- **Whether MUI X `exportState`/`restoreState` is available in the MIT package.** Inferred from the absence of any `plan-pro`/`plan-premium` badge in `docs/data/data-grid/state/state.md` [M5]. Absence of a badge is weaker than a positive statement; confirm against `mui.com/x/react-data-grid/state/` rendered, or by checking whether `exportState` is declared on `GridApiCommunity`.
- **AG Grid screen reader announcement of the sort _index_** in a multi-sort. `aria-sort` carries direction only, and the `ag-sort-order` span is `aria-hidden="true"` in the header template [A9], which suggests the priority number is not announced — but no AG Grid doc was found stating this either way.
- **Whether AG Grid's `sortIndex` renders as a visible number by default or only with a custom header component.** The `ag-sort-order` element was read from the **column-header-components** docs page's template examples [A9], not from a page stating the default header renders it. Confirm by reading `packages/ag-grid-community/src/headerRendering/` or by inspecting a live default-header multi-sort.
- **TanStack `sortUndefined` and `null`.** The source check is unambiguous (`aValue === undefined` [T2]), but no TanStack doc states that `null` is deliberately excluded rather than overlooked. This is a reasonable inference from code, not a doc-confirmed design statement.
- **PrimeNG passing `this.sortOrder` as the `nullSortOrder` argument** [P2][P3]. Read from shipped code; whether it is intentional is not stated anywhere. Reported as an observation, not a defect claim.
