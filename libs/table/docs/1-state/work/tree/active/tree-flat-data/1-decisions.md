# tree-flat-data — decisions (#163)

`withTree()` builds its hierarchy from flat `data()` (E5).
Source: [#163](https://github.com/DvirMon/ng-table/issues/163).
Capability log: [`decisions/tree.md`](../../../../../decisions/tree.md) (TR-rows; first logged as E20–E37 in `decisions/expansion.md`).

## Dependency ranking

Nodes, with edges (B needs A's decision → A → B):

- **N1 config shape** (parent-id accessor, collapse-only, `isExpandable`) — core

- **N3 expandability + discovery source** (`isExpandable` default, `expand()`/`state` scan input) — dependent: N1, N2
- **N4 composition with `withGrouping()`** (parent and child in different groups) — dependent: N2

## Decisions

- **D1** (2026-09-27, N1) — `WithTreeConfig.childrenAccessor` is replaced by `parentId?: (row: TRow) => RowId | null | undefined`. `null`/`undefined` means root. Named like `trackBy` (returns an id), no `Accessor` suffix. Omitted still means collapse-only with no `'tree'` stage claimed (E13 carried over). Log: E20.
- **D2** (2026-09-27, N2) — Orphan rule not decided yet. It is a UX decision, and it may need several modes (promote to root, drop, keep ancestors, filter children only). Blocked on product discovery: `discovery-tree-filter-community.md`, `-competitors.md`, `-internal.md` in this folder. N3, N4 and N5 wait for it. — resolved by D5.
- **D3** (2026-09-27, N6) — Hard break: `childrenAccessor` is deleted with no deprecation window. No `flattenTree` helper is exported — flattening nested data is consumer-owned data prep; `tree.md` shows a short flatten snippet instead. Log: E21.
- **D4** (2026-09-27, N5) — A broken parent link degrades to root (ADR-0014: runtime, data-dependent → degrade, never throw). Covers: `parentId` throws for a row; a row names itself as parent; a cycle (the first row of the cycle in input order becomes root); a parent id not present in `data()`. The row renders at depth 0 with its own subtree intact, and each kind is reported once per evaluation, in production too. Hiding was rejected — a missing row goes unnoticed. Log: E22.
- **D5** (2026-09-27, N2) — Filtering a tree keeps each match plus its ancestors, as context rows (default). A boolean `includeDescendants` opts in to also keeping every descendant of a matched row. Grounded in the three `discovery-tree-filter-*.md` files: all six surveyed libraries keep ancestors; they split only on descendants (AG Grid/PrimeNG yes by default, MUI/TanStack/DevExtreme/Syncfusion no). Leaf-only mode not adopted. Consequence: filtering never creates an orphan — orphans come only from broken data (D4). Resolves D2. Log: E23.
- **D6** (2026-09-27, N2) — Ancestor retention lives in an engine slot. `withTree()` contributes a parent link (`parentOf`) to the engine, mirroring `expandedRows`. The `filter` stage reads the slot when present and keeps ancestors (plus descendants under `includeDescendants`). Neither feature reads the other's state. `includeDescendants` sits on `withFiltering()`, the feature whose output changes. Rejected: `withFiltering({ parentId })` (the same accessor configured twice, can drift), and a `withTree()` stage after `filter` that re-adds rows (post-filter counts and select-all would disagree with what renders). ADR: [0028](../../../../../adr/0028-tree-parent-link-slot.md). Log: E24.
- **D7** (2026-09-27, N2) — Glossary term: **context row** — a row shown only because one of its descendants matched the filter. Added to `libs/table/CONTEXT.md`.
- **D8** (2026-09-27, N3) — While a filter is active, `tree.expand()` with no ids and `tree.state` scan the filtered view only (matches and context rows) — "expand all" opens what the person sees. A boolean `includeHidden` scans all of `data()` instead, matching `selectAllIds()`'s default and flag. Log: E25.
- **D9** (2026-09-27, N3) — Without `isExpandable`, a row's computed `hasChildren` is true only when it has children in the filtered view. A parent whose children are all filtered out gets `hasChildren: false`, so the UI renders no toggle. A consumer `isExpandable` still overrides the computation (lazy children). Log: E26.
- **D10** (2026-09-27, N4) — Grouping + a `parentId` tree (a child whose group value differs from its parent's) is not decided yet. Candidates: follow the root (today's behavior), split by the row's own value, or disallow the combination. Blocked on discovery: `discovery-tree-grouping-products.md` (end-user products: Monday, Jira, Asana, ClickUp, Notion, Airtable, Smartsheet, Linear) and `discovery-tree-grouping-competitors.md` (grid libraries). — resolved by D13.
- **D11** (2026-09-27, N8) — Every tree node is a row: `totalRowCount` (and `aria-rowcount`) and `selectAllIds()` count children like any row, collapsed or not; only filtered-out rows are excluded. Group-header aggregates wait on D10. Log: E27.
- **D12** (2026-09-27, N5) — Removing a parent row is not special-cased: its children keep a parent id absent from `data()` and degrade to root per D4. `withTree()` exposes a read-only `table.tree.descendantsOf(id): RowId[]` (walks `parentId` over `data()`); a consumer wanting a cascade composes `removeRows([id, ...table.tree.descendantsOf(id)])`. `removeRows` stays tree-agnostic; the tree slice never writes rows. Rejected: `removeRow` cascading when `withTree()` is composed (a write whose effect depends on which features are present). Log: E28.
- **D13** (2026-09-27, N4) — Grouping + a `parentId` tree groups roots only; each subtree follows its root's group, whatever the descendants' own values — the tree is never split. The `group` stage reads the ADR-0028 parent-link slot to find roots (its second consumer after `filter`). A flat per-row grouping needs no flag: compose `withGrouping()` without `parentId`. Rejected: a flat flag on `withGrouping()` (duplicates omitting `parentId`); disallowing the combination. Grounded in `discovery-tree-grouping-competitors.md` (no library regroups a child by its own value; TanStack follows the root) and `discovery-tree-grouping-products.md` (products keep the tree whole by default; per-row grouping is always an opt-in flat mode). Resolves D10. Log: E29.
- **D14** (2026-09-27, N8) — With grouping + tree, a group header's row count includes every node in the group, descendants too — consistent with D11, so group select-all selects the number shown. Rejected: roots only (Wrike's choice; would disagree with `totalRowCount`). Log: E30.
- **D15** (2026-09-27, N8) — Group aggregates stay agnostic: `aggregate(path.x, aggregateFn)`'s `rows` holds every node in the group, descendants included. Whether a parent's value is its own or a roll-up is the server's data model; the consumer's `aggregateFn` applies it (e.g. sum leaves only by excluding rows that are some row's parent). No new mechanism. Rejected: passing leaves only or roots only — either makes one data model impossible to express. The tree fixture's roll-up parent (`d4` = 42000) is fixed so parents carry their own amounts. Log: E31.
- **D16** (2026-09-27, N3) — While a filter is active, context rows render expanded so every match is visible. Visibility rule only: `table.tree()` (the open set) is not written and `changed` does not fire; clearing the filter restores the person's own expand/collapse state exactly. Rejected: writing context ids into the open set (DevExtreme `expandNodesOnFiltering`; leaves rows open after clear, emits per keystroke); doing nothing (matches hidden under collapsed rows — the complaint in `discovery-tree-filter-community.md`). Log: E32. — superseded by D20.
- **D17** (2026-09-27, N3) — Toggling a revealed context row (D16) collapses it. The table keeps a separate "collapsed during this filter" set, apart from the open set; it resets when the filter changes or clears. The toggle always does what it shows. Rejected: a disabled toggle (looks broken); writing the open set (mixes saved state with the temporary reveal). Log: E33. — superseded by D20.
- **D18** (2026-09-27, N3) — `RenderRow` carries `isContextRow: boolean` (true only for a context row under an active filter). `ngpTableRow` exposes it as the presence attribute `data-context-row` (`'[attr.data-context-row]': "ngpTableRow().isContextRow ? '' : null"`), per ADR-0026 rule 1 — never `="true"`/`="false"`. Styling stays the consumer's. First boolean presence attribute on rows (expansion is `aria-expanded` only today). Log: E34. — amended by D20 (adds `contextRowIds()`). — directive owner amended by D21.
- **D19** (2026-09-27) — Scope and complexity. Out of #163: duplicate row ids (#156); selection cascading from a parent to its children (open question in `0-product/tree.md`). Settled by the issue body, not re-decided: siblings keep input order so pipeline sorting carries over; lazy children arrive by appending rows to `data()`. `isComplex: true` — a new engine slot (ADR-0028) consumed by `filter` and `group`, a per-filter collapsed set, a new `RenderRow` field and directive attribute; the work spans `withTree()`, `withFiltering()`, `withGrouping()`, the engine and `ngpTableRow`, so `/to-issues` will likely split it.
- **D20** (2026-09-27, N3) — Filter reveal is a derived, declarative default with an imperative escape hatch. (a) Reveal is a computed visibility source unioned into `expandedRows` — it never writes the open set and vanishes when the filter clears, so no snapshot/restore. (b) `withTree({ revealContextRow?: (row: TRow) => boolean })` picks which context rows reveal; default reveals all; `() => false` turns reveal off. A row predicate on the `withTree()` config like `isExpandable`, not a `schema` rule — schema paths name columns (ADR-0027 rule 1), reveal is about rows. (c) Toggling a revealed row closes it via an internal set whose entries live only while that row is a context row — ids drop out automatically when the row stops being context or the filter clears; no reset-timing policy. (d) Facts exposed as reads on `table.tree`: `contextRowIds()`, `parentOf(id)`, `descendantsOf(id)` (D12), plus `RenderRow.isContextRow` (D18). (e) Principle: every fact only the library can compute is exposed; every policy has a declarative default that can be switched off, after which any behavior (reset on keystroke, stay open after clear, custom memory) is rebuilt from the facts plus `expand`/`set`/`toggle`. Grounded in `0-product/tree.md` §2.2 / OQ-2 (D17's reset-on-change reopened a row the person had closed on every keystroke). Supersedes D16, D17. Log: E35.
- **D21** (2026-09-27, N3) — `data-context-row` is bound by a new minimal tree feature directive, `ngpTableTreeRow` (`tr[ngpTableRow][ngpTableTreeRow]`, `div[...]` likewise), not by core `ngpTableRow` — per `libs/table/CLAUDE.md` "RenderRow field ownership by directive layer": `isContextRow` is optional and feature-contributed. In #163 it binds only `data-context-row`; the wider tree UI (`aria-level`, indentation, toggle) goes to a separate issue for the unowned tree UI spec (`0-product/tree.md` gap analysis). Log: E36.
