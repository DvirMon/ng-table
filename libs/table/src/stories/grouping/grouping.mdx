# Grouping

One story, one lesson, one canvas — in the order worth reading them. Most are `withGrouping()`'s
own surface; three compose it with exactly one more feature.

**`Basic` is the one to copy.** Its host composes `withGrouping({ initial })` and nothing else, so
nothing in its source is another lesson's setup — no predicate it does not need, no second feature,
and no `aggregate`, because a baseline carrying scenery is how a reader mis-attributes an
option to the wrong place.

Each story composes the fewest features its lesson needs. Where a second feature does appear —
`withSorting()` in `Order`, `withTree()` in `Collapsible`, `withFiltering()` in `Group
selection` — the page says what it is there to make visible.

Shared across all of them: `fixtures/schema.ts` (one column list, one `groupingConfig`, and the
grouping levels that do differ per story), `fixtures/http.ts` (the intercepted round trips),
`grouping-story.pipes.ts` (one pure pipe per formatting concern, so no host formats in a method)
and `grouping-story.css`. Those are at the bottom of this page, once.

## Basic — the whole feature, with nothing else on

`withGrouping({ initial })` and nothing else: no schema, no predicate, no second feature — and
deliberately no `withTree()`, because a chevron with nothing to expand is a control that does
nothing. Array order is nesting order.

Group headers carry value and count. No `amount` total, because totals are the `Aggregates`
story's lesson (`aggregate`) and it has its own story below; scenery on a baseline is how a
reader mis-attributes an option.

The tab strip toggles a column as a level; the pills below reorder and remove them. One control per
column, one boolean state, so adding a duplicate level is unreachable from the UI rather than a
no-op to explain. Every write is an updater on `table.grouping`.

## When — which clusters survive

Two predicates, AND-combined: the table-wide `when`, judged at every active level, and a
per-column one off a `grouping` rule, judged for its own column only.

A rejected cluster is **not hidden**. Its rows render flat at the parent's depth with no header,
no group id and no aggregates — which is why rejecting at level 1 also takes those rows out of
level 2: they left the tree, so there is nothing left to sub-group. The on-canvas count of
depth-0 rows is there to make that legible without counting by eye.

Both predicates read signals *inside* the callback rather than being rebuilt, so the toggles are
reactive without reconstructing the table.

## Keys — what a level clusters on, and what its header calls itself

Two declarators, one lesson: `groupKey` decides the group **key** a level clusters on;
an `initial` entry's `label` decides what its header **calls itself**. Bundled in one story
because they answer adjacent questions a reader could otherwise conflate — not because either
is large on its own.

`Sales Region` carries an explicit `initial` label and wins over its column's own. `Closed` has
none, so it falls back to the `closedAt` column's own label — two tiers, both visible in one
render. Every level names a declared column (ADR-0024); there is no longer a third, raw-field-name
fallback for one that doesn't.

`groupKey` buckets `closedAt` into a `YYYY-MM` string, so twelve distinct timestamps
collapse into five month groups. Turning it off in Controls groups on the exact `Date` instead —
the engine never coarsens a key on its own. The extractor receives the column's own accessor
output, not the raw row field — for `closedAt`'s plain accessor the two are the same value, which
is why this reads as a no-op story for it, but a derived-accessor column would receive that
computed value instead.

## Aggregates — totals at every depth

Aggregation is a grouping declaration, keyed by declared column id like every other data concern
a `schema` records — not a column option. `aggregate(path.amount, sumAmount)` is what lets
`amount` carry a total, and the same mechanism works on a column with no row field of its own to
compute it from.

A parent total is the sum of its own leaves, not of the headers beneath it — so there is no
blank-at-depth-0 hole. Aggregates are post-filter by construction, since `filter` precedes `group`
in the pipeline; the control that proves it lives in `Group selection` below, which composes
`withFiltering()` for its own reasons.

The toolbar poisons one row so `sumAmount` throws on it. Per ADR-0014 the table stays up: that one
column's aggregate falls back to `undefined` for the affected groups, reported once per column per
evaluation rather than once per group, with every other column untouched.

## Async Rule — a level decided by the server

One grouping level over a real intercepted request, through an `groupingAsync()`-shaped column
rule. The point is the *pending* window, which is otherwise invisible: while the rule is unresolved
the whole rule set abstains and the table holds the grouping it was given, rather than flashing
ungrouped and back. On resolution the level set becomes the rule's — a resolved rule overrides the
base choice rather than merging with it.

`onError` is required to return an explicit boolean: `false` here, resolving the set to `[]`, which
is "grouped by nothing" rather than "no answer yet", and leaves every row on screen. Turn on
`forceFailure` in Controls to see it — one boolean away from the resolved case, so it is a control
rather than a second canvas.

## Order — which sibling comes first

`groupOrder` orders group **headers** among their siblings at one level. Not the rows inside a
group, which is `withSorting()`. Not which groups exist, which is `when`. Not which columns are
levels, which is `initial`.

With no comparator, siblings keep **first-occurrence** order — the order each key was first seen
while scanning the rows. The comparator receives a `GroupSummary`, not a row, and its `rows` field
is the cluster's own leaves; that is what makes `by-count`, or ordering by a total, ordinary code.
`external-list` is the shape a saved report or a pinned-priority list takes, with unlisted values
sorting last.

`throwing` sits last in the select because nobody picks it deliberately: the comparator throws on
every sibling pair it is handed and the table does not go down. Per ADR-0014 the clustering sort
catches, falls back to stable first-occurrence order for the affected levels, and reports once per
evaluation. The fallback *is* first-occurrence, so headers follow the row sort again — a
comparator that throws pins nothing.

A comparator is also declared for `Rep`, which is not a level by default. It is inert until the
canvas button adds it — **`groupOrder` never activates a level**, which is the whole split
from `grouping`.

This story also composes `withSorting()`, bare and trailing, because the header order is only
legible next to the row sort it is not. Under `first-occurrence` a header click moves the
**headers** — siblings still follow the rows' own scan order. Under a real comparator, headers
hold: sorting a column inside a group reorders its rows while the header stays put, and sorting a
level column itself moves nothing at all, because every row under one of its groups holds the
same value.

## Columns — what happens to a column once it becomes a level

`withGrouping()` does not touch the column list, and takes no position on whether a grouped column
keeps its place. All three dispositions — keep, hide, move to front — are consumer code over
`toggleColumnVisibility` and `reorderColumns`.

`hide` sets `visible: false`; the column stays in `table.columns()`, so the disposition reverses
cleanly when the level comes off. `columns()` is the folded list rather than a render order — it
carries `visible` and `order` and leaves the reading to whoever renders it, which is why
`move-to-front` is a write to `order` and not the table re-sorting itself.

## Collapsible — the navigable outline

`withGrouping()` + `withTree()`, and nothing else: group headers bind
`[ngpTableRow]="row" ngpTableTreeRow`, with buttons carrying `ngpTableTreeToggle` to manage
expansion. A deal linked to line items via `parentId` renders a second, separately-keyed chevron
from the `'tree'` stage.

Expand All is the reason `groupIds()` exists. `tree.expand()` on its own discovers data rows through
`parentId` links and cannot reach a group header, so the outline needs
`tree.expand(table.groupIds())` — and `groupIds()` derives from the cluster tree rather than from
`renderRows()`, so it finds every header at every depth no matter what is collapsed right now.

Group headers and data rows both read `row.isExpanded` — `flattenVisible()` stamps it on every
render row once a composed feature contributes the expansion slot.

<Canvas of={CollapsibleStories.Collapsible} />

Regroup re-nests the three levels, so every group id changes at once and the outline visibly
rebuilds. `forceFailure` in Controls makes Refetch fail every time instead of returning a fresh
page. That collapse state survives a refetch or a sort is asserted in `with-grouping`'s spec
rather than shown here — a control whose whole outcome is "nothing moved" gives a reader nothing
to look at.

Group headers and data rows bind the tree directives alike. Both read `row.isExpanded`
since `flattenVisible()` stamps it on every render row.

## Group selection — the cascade, over one `rowsOf()`

The `cascade` control is this story's whole argument, not a convenience. D16 made the
group-selection cascade consumer-owned precisely because the major libraries ship different
defaults, so a single hardcoded cascade in a story would read as the library taking a position it
deliberately does not take. Both modes are ordinary code over one `rowsOf()` call, with tri-state
group checkboxes derived rather than stored, and a readout proving no group header is ever in the
selection.

MUI X's both-directions default is not a third mode, because reaching parents needs no write: a
group's tri-state derives from `selectionStateOf()` every render, so an ancestor turns from
indeterminate to checked on its own. A radio option that changes nothing on screen teaches that
worse than one sentence does.

`withFiltering()` is composed here for a reason the other stories do not have — it makes
"`rowsOf()` is post-filter by construction" visible. Filter a rep out and every group's checkbox
and count follow the rows that survived.
