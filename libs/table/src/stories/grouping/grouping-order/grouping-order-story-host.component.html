groupOrder orders group headers among their siblings at one level — not which groups exist, which is when, and not which columns are levels, which is initial. Clicking a column that is a level can only ever move headers, never rows, because every row under one of its groups holds the same value — whether it moves them at all is what the comparator decides. Pick a comparator in Controls.

No ordering opinion — the comparator returns a constant 0 and the sort is stable, so siblings keep the order each key was first seen while scanning the rows. This is also what you get by declaring no comparator at all. The rows reach clustering already sorted, so the headers inherit the row sort.

b.rows.length - a.rows.length — biggest cluster first. GroupSummary.rows is the cluster's own leaves, which is what makes ordering by size, or by a total, possible at all. Headers stay in size order; a row sort never reaches this comparator.

} @case ('external-list') {

A caller-supplied ranking — {{ externalOrder.join(' → ') }} — with values absent from it sorting last. The shape a saved report or a pinned-priority list takes. That order survives every row sort applied on top of it.

} @case ('throwing') {

The comparator throws on every sibling pair it is handed, and the table is still up. Per ADR-0014 the clustering sort catches, falls back to stable first-occurrence order for the affected levels, and reported it once for this evaluation, to the console. The fallback is first-occurrence, so headers follow the row sort again — a comparator that throws pins nothing.
